When pull requests are spread across several repositories, a flat list loses
the relationships I care about. Which organization owns the target? Which
repository contains the branch? Is a change waiting on another PR? Did the head
branch come from a fork?

I made a small PlantUML include that keeps those ideas visible without repeating
all of the shape and color declarations in every diagram. The repositories and
pull requests below are synthetic.

## Use short pull-request specs

The library understands three forms of pull-request reference:

| Form               | Meaning                                |
| ------------------ | -------------------------------------- |
| `acme/payments#41` | Owner, repository, and PR are explicit |
| `payments#42`      | Reuse the default owner                |
| `#43`              | Reuse the default owner and repository |

Set the defaults once, open an owner and repository container, then add branches
and PRs:

```plantuml alt="Three stacked pull requests inside an Acme payments repository, connected to their head and base branches"
@startuml
!include ../../../../plantuml/github-pull-requests.puml

$GHPR_DEFAULTS("acme", "payments")

$GHPR_OWNER_BEGIN("acme", "organization", "org_acme")
$GHPR_REPO_BEGIN("", "repo_payments")
$GHPR_BRANCH("main", "branch_main", "base branch")
$GHPR_BRANCH("feature/payment-api", "branch_api", "head branch")
$GHPR_BRANCH("feature/payment-retries", "branch_retries", "head branch")
$GHPR_BRANCH("feature/payment-metrics", "branch_metrics", "head branch")

$GHPR_PR("acme/payments#41", "Add authorization API", "feature/payment-api", "main", "approved", "pr_41", "PAY-101\nAdd authorization API\nApproved\nfeature/payment-api -> main", %true())
$GHPR_PR("payments#42", "Retry declined payments", "feature/payment-retries", "feature/payment-api", "review-required", "pr_42", "PAY-102\nRetry declined payments\nReview required\nfeature/payment-retries -> feature/payment-api", %true())
$GHPR_PR("#43", "Record retry metrics", "feature/payment-metrics", "feature/payment-retries", "draft", "pr_43", "Record retry metrics\nDraft\nfeature/payment-metrics -> feature/payment-retries", %true())
$GHPR_END()
$GHPR_END()

$GHPR_JIRA_BEGIN("Jira", "jira_tickets")
$GHPR_JIRA("PAY-101", "", "https://jira.example.test/browse/PAY-101", "Payment authorization\nReferenced by acme/payments#41", "jira_pay_101")
$GHPR_JIRA("PAY-102", "", "https://jira.example.test/browse/PAY-102", "Declined payment retries\nReferenced by acme/payments#42", "jira_pay_102")
$GHPR_END()

$GHPR_OPENS(branch_api, pr_41)
$GHPR_OPENS(branch_retries, pr_42)
$GHPR_OPENS(branch_metrics, pr_43)
$GHPR_TARGETS(pr_41, branch_main)
$GHPR_TARGETS(pr_42, branch_api)
$GHPR_TARGETS(pr_43, branch_retries)
$GHPR_STACK(pr_41, pr_42, "stack position 1 -> 2")
$GHPR_STACK(pr_42, pr_43, "stack position 2 -> 3")
$GHPR_REFERENCES(pr_41, jira_pay_101)
$GHPR_REFERENCES(pr_42, jira_pay_102)
$GHPR_LEGEND()
@enduml
```

The macros deliberately keep aliases separate from labels. Human-readable specs
appear in calls and links, while stable aliases such as `pr_41` make relationship
lines uncomplicated.

PR nodes are compact in this example. Hovering their linked number reveals the
title, review state, branches, and ticket key. Jira tickets use purple cards and
their own hover text, keeping issue context available without widening every
node.

## Keep fork branches with their source repository

A cross-repository PR belongs to two places. Its branch lives in the fork, but
the pull request itself targets the upstream repository. The diagram can show
both facts:

```plantuml alt="A documentation branch in a contributor fork opening a pull request against the Acme payments repository"
@startuml
!include ../../../../plantuml/github-pull-requests.puml

$GHPR_DEFAULTS("acme", "payments")

$GHPR_OWNER_BEGIN("acme", "organization", "org_acme")
$GHPR_REPO_BEGIN("acme/payments", "repo_upstream")
$GHPR_BRANCH("acme/payments:main", "branch_main", "base branch")
$GHPR_PR("#55", "Document payment webhooks", "docs/webhooks", "main", "review-required", "pr_55")
$GHPR_END()
$GHPR_END()

$GHPR_OWNER_BEGIN("dev-forks", "user", "owner_contributor")
$GHPR_REPO_BEGIN("dev-forks/payments", "repo_fork", "acme/payments")
$GHPR_BRANCH("dev-forks/payments:docs/webhooks", "branch_docs", "head branch")
$GHPR_END()
$GHPR_END()

$GHPR_OPENS(branch_docs, pr_55)
$GHPR_TARGETS(pr_55, branch_main)
$GHPR_FORK(repo_fork, repo_upstream)
$GHPR_LEGEND()
@enduml
```

`$GHPR_OWNER_BEGIN`, `$GHPR_REPO_BEGIN`, and `$GHPR_END` produce the nested
containers. The smallest shapes remain branches and pull requests; connections
between them carry the workflow.

## Import the same library elsewhere

The include is
[`plantuml/github-pull-requests.puml`](https://github.com/imochoa/astro-blog/blob/main/plantuml/github-pull-requests.puml).
Use `!include_once` when a larger diagram might import it through more than one
path. PlantUML procedures support default and keyword arguments, so the optional
title, branch, status, and alias values can be omitted or named when a diagram
needs less detail.

The complete macro reference, accepted spec forms, and status names live in the
repository's `docs/github-pr-plantuml.md` file.
