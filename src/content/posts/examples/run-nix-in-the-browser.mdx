I went looking at [Tour of Nix](https://nixcloud.io/tour/?id=introduction-tour)
expecting to find a server behind its Run button. There isn't one. The page
really does run a Nix evaluator in the browser, although the machinery is older
than WebAssembly.

I wanted the same immediate feedback in a post without copying a 2015 build of
Nix, so I used Tvix for the live example below.

<NixPlayground client:visible />

The evaluator is downloaded after the first click. It runs locally and the page
does not send the expression anywhere. This is a language playground rather than
a Nix shell: it cannot build a derivation, fetch nixpkgs, or install a package.

## How Tour of Nix runs Nix

Tour of Nix bundles `nix-instantiate` from Nix 1.9. Its authors modified the C++
program to remove dependencies that did not work in a browser, then compiled it
with Emscripten 1.29.10. Their
[build notes](https://lastlog.de/blog/tour_of_nix.html) show the command and the
changes they had to make.

That version of Emscripten produced asm.js: a restricted, optimizable subset of
JavaScript. WebAssembly was not yet available. The files currently served by the
tour make the cost visible:

| File                     | Uncompressed size | Purpose                                       |
| ------------------------ | ----------------- | --------------------------------------------- |
| `nix-instantiate.js`     | 4.8 MB            | The compiled evaluator and Emscripten runtime |
| `nix-instantiate.data`   | 24.3 MB           | Files preloaded into the virtual filesystem   |
| `nix-instantiate.js.mem` | 55 KB             | Initial contents of the asm.js heap           |

The generated JavaScript asks for a 350,777,216-byte heap, about 335 MiB. Most
of the download is the data archive because it contains a copy of nixpkgs. That
lets the exercises import functions from `pkgs/lib` while remaining offline
after the first load.

When Run is pressed, the page writes the editor contents to `/test.nix` in
Emscripten's in-memory filesystem. It then calls the compiled program with the
equivalent of:

```sh
nix-instantiate \
  -I nixpkgs=nixpkgs \
  --eval --strict --show-trace \
  /test.nix
```

The page replaces the program's stdout and stderr handlers so the result and
diagnostics appear under the editor. There is no container, Nix daemon, or
remote execution service involved.

This is a clever bit of browser archaeology, but I would not use the generated
binary in a new component. The repository's README says the modified Nix source
was lost. Rebuilding or updating it means reconstructing the old port first.

## Use Tvix for a current evaluator

[Tvix](https://tvix.dev/) includes a Nix-compatible evaluator written in Rust.
Its [Tvixbolt playground](https://bolt.tvix.dev/) already compiles that
evaluator to WebAssembly. The
[`nix-eval`](https://github.com/dvcorreia/nix-eval) package wraps the same
evaluator for use from JavaScript:

```sh
pnpm add nix-eval
```

```ts
import { createEvaluator } from "nix-eval";

const evaluator = await createEvaluator({ strict: true });
const result = await evaluator.eval("6 * 7", "example.nix");

console.log(result.output); // 42
console.log(result.errors);
```

Its browser Wasm module is about 3.3 MB uncompressed. The API also returns the
parsed expression, generated bytecode, warnings, and a runtime trace. The
playground puts those under the "Evaluator internals" disclosure so they do not
crowd the usual result.

`strict: true` forces the final value before it is rendered. Without it, lazy
values inside a list or attribute set may appear as `<CODE>` rather than their
contents.

## Keep evaluation off the main thread

A Nix expression can take a long time or never finish. Calling the evaluator in
the component's own script would block input and scrolling until it returned.
The playground creates a module worker instead:

```ts
// NixPlayground.worker.ts
import { createEvaluator } from "nix-eval";

const evaluatorPromise = createEvaluator({ strict: true });

evaluatorPromise.then(() => self.postMessage({ type: "ready" }));

self.addEventListener("message", async (event) => {
  const evaluator = await evaluatorPromise;
  const result = await evaluator.eval(event.data.source, "playground.nix");
  self.postMessage({ type: "result", id: event.data.id, result });
});
```

The Svelte component starts that worker on the first run:

```ts
const worker = new Worker(
  new URL("./NixPlayground.worker.ts", import.meta.url),
  { type: "module" },
);
```

Vite emits the worker and Wasm binary as fingerprinted assets. The component
waits for the worker's `ready` message before starting a three-second evaluation
timer. If the timer expires, it terminates the worker. A fresh worker is created
for the next attempt. Terminating a worker is the useful part here: a Promise
timeout alone cannot interrupt synchronous Wasm code.

The component is imported into this MDX file as a visible Svelte island:

```mdx
import NixPlayground from "@/components/blog/NixPlayground.svelte";

<NixPlayground client:visible />
```

`client:visible` delays the Svelte code until the playground approaches the
viewport. The larger Wasm module still waits for a click because the worker does
not exist before then.

## What this playground cannot do

The package creates Tvix's pure evaluator. Language features such as functions,
lists, attribute sets, and pure built-ins work. Operations that need a Nix
store, filesystem access, network fetches, or process execution do not.

A browser can evaluate `map (x: x * 2) [ 1 2 3 ]`. It cannot turn a flake into a
development shell. Doing that would require a backend with a real Nix store and
a carefully restricted execution API, which is a different project with a much
larger security boundary.
